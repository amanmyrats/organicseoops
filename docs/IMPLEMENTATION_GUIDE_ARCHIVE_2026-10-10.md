## 1. Start Or Resume In Any Model

### Default continuation policy (D068)

D423 clarifies D375: full suites belong only to an explicitly selected final app-ready/release validation phase or explicit user request. New sessions, timer launches, repairs and unfinished full-validation cards never trigger a full run. Record source/configuration target, scope, reason and owner, and reuse evidence until relevant changes invalidate it. Default continuation defers full acceptance while independent authorized implementation remains. Reconcile an existing broad run once, protect its actual source/database/service dependencies, then continue independent work without waiting or polling; collect genuine terminal evidence when available. Known failed contracts block their actual dependents, and required full acceptance remains unfinished before release.

D425 makes check selection explicit: command maps and old card/checkpoint receipts are coverage references, not instructions to replay them. Choose exact changed-behavior methods/cases or one genuinely small owning file; `quicktest` does not make app-wide labels focused. Reuse passing evidence for unchanged source/configuration. Consult recorded runtimes before expensive checks, narrow to the affected contract and defer non-gating slow coverage to its coherent-feature/final-validation trigger. Documentation-only and trivial changes need only relevant static checks. Run system/migration checks, worker reloads, runtime probes and builds only when their actual boundary changes or a required state-changing gate needs them. Preserve sensitive-boundary checks and known-failure gates; never silently skip coverage, weaken assertions or record deferred acceptance passed.

D375 sets verification timing for every card: focused changed-behavior checks during coding, affected regression at coherent feature checkpoints, and full suites at app-ready validation. Read `AGENTS.md` Verification cadence before selecting checks; older per-slice/full-suite wording is superseded for timing, not coverage. Record deferred required acceptance and continue local coding through implemented, focused-checked interfaces without declaring unverified cards done.

The reusable entry point is [CONTINUE.md](../CONTINUE.md); the user can simply say “follow CONTINUE.md.” Continue sequentially across dependency-ready implementation cards within recorded authorization, with no fixed card limit unless the user requests a narrower task or batch. Finish partial work that can safely be completed; after each card's local implementation acceptance and status updates, immediately select the next eligible card using Section 4. A completed card/checkpoint, missing real provider key/account, example domain or AWS access is not a coding stop. D103 replaces D100's credential-request stopping rule: implement UI-configurable provider/model/billing flows and checked deployment artifacts with safe local contract/fixture tests, while recording unrun live-provider/hosted/public **release** evidence separately. Never call fixtures live acceptance, bypass feature dependencies or record secrets in the handoff.

Stop when the requested task/batch is complete or the user asks to pause; no eligible authorized implementation work remains after searching the backlog; or an actual context/tool/session limit requires a handoff. At exhaustion, record unrun external release checks and the operator UI/runbook that will eventually configure them; do not request credentials to complete code. Record stopping reason and exact next action. Card complexity and session capacity determine how many cards finish; no minimum count is promised. This policy does not expand deployment, paid-call or Git authorization. Use Section 5.2's reusable development loop and Section 6's affected-check policy.

D323 explicitly permits global no-approval/full-access Codex CLI defaults on this host, with scheduled sessions inheriting them; see [.agents/README.md](../.agents/README.md) for the current adapter. This changes execution access, not product authority, acceptance gates or local/provider/deployment/Git boundaries.

The one-minute checks, D124/D131 guards and D326 five-window retention continue; D381 permits idle managed sessions to stay open while a new timer session starts, using project-wide native status plus startup/native-child identity guards. This is a launch-time snapshot, not per-client mapping or enforced serialization of later manual resumes. Native Codex history holds conversation evidence; the private run log is a notice, not a screen transcript. See [.agents/README.md](../.agents/README.md) for host commands. D325/D326 non-interactive streaming evidence remains historical.

At genuine local-work exhaustion, follow [CONTINUE.md](../CONTINUE.md)'s pause protocol **after** final checkpoint/ledger/TODO updates (D131). ## 4. Execution Order And Release Gates

Task dependencies take precedence over the numeric order of TODO phases. Phase numbers match TODO; the canonical plan's roadmap is coarser (plan Phase 2A = TODO Phase 3A, plan Phase 7A = TODO Phase 11A).

### Practical execution lanes

1. **Foundation:** `P01-01` through `P01-06`, then accounts/tenancy (`P02-01`–`P02-05`) and baseline administration (`P03-01`). Git initialization inside `P01-01` is conditional on a separate request.
2. **Design and decisions:** `P01-07`, `P3A-01`–`P3A-04` can progress alongside the foundation as decisions become available. Account/app wireframes can precede launch positioning; final public copy/wireframes depend on accepted positioning.
3. **Durable execution:** `P04-01`–`P04-05`, then providers (`P05-*`) and core project/source work (`P06-01`–`P06-06`). Introduce credential/storage helpers with their first real consumer, not as empty frameworks.
4. **SEO value:** safe crawl/performance (`P07-*`), findings/mapping/action/outcomes (`P08-01`–`P08-06`), research/briefs (`P10-01`, `P10-02`). Trends and the full draft editor are not prerequisites to a brief for a manually selected opportunity.
5. **Commercial completion:** finish trial/billing/enforcement/public pages/email/funnel work (`P3A-*`), onboarding first value (`P06-07`), reports/support (`P08-07`–`P08-09`), closure (`P02-06`), staff operations (`P03-02`, `P03-03`), and production deployment (`P13-*`). Complete `GATE-PUBLIC` before public trials or payment acceptance.
6. **Expansion:** Bing/Yandex, trends, drafts/social variants, expanded competitors/local/logs, AI visibility, and passive security follow their actual dependencies and prioritization. A launch only advertises features whose own gates are satisfied. Phases 14–16 require demonstrated need/authorization rather than blocking the internal core release.

Build and locally simulate OAuth, billing sandbox, static/CDN rules and email delivery before any hosted environment exists; actual staging/deployment checks belong to release and require explicit access/authorization. Deployment-preparation cards need not wait for optional features. Production exposure still depends on the public gate. Internal cost limits and usage accounting apply from the first expensive job.

## 7. Durable Checkpoint And Recovery Protocol

### Task states

`pending` → `in_progress` → `done`, with `blocked` for an unmet **implementation** dependency/decision/environment and `deferred` only for an explicitly recorded postponement. `blocked` and `deferred` preserve the unfinished requirement; missing provider account, user example project or live deployment is release evidence rather than a coding dependency under D103. One primary active implementation card at a time unless parallel work is explicitly requested and isolated; record all owners in that case. This is a concurrency rule, not a one-card-per-session limit; follow Section 1's continuation policy. Under D375, a prior card may stay `in_progress` with code complete/focused checks passed and broader verification deferred while the next card is actively coded. Record the actual dependency contract and pending check trigger; do not mark either deferred checks or failed prerequisites accepted.

### Checkpoint cadence

Update [IMPLEMENTATION_STATE.md](IMPLEMENTATION_STATE.md):

- At task start, before a migration/provider/deployment operation, and when a decision/blocker changes.
- After each meaningful code-and-check slice, not only at the end of a session.
- Before switching tasks/models, when context is nearly full, and before stopping.

For the active task record: completed substeps, next incomplete substep, touched paths, unverified edits, actual test commands/results, blockers, process/job IDs, environment, migration status, external effects, safe retry information, and next exact action. Avoid secrets, tokens, customer payloads and signed URLs in all handoff records. Provider names, safe request/job identifiers and references to secured evidence are enough.

Under D322, keep the checkpoint as a compact current handoff (about 150–200 lines when practical), replacing superseded current summaries rather than prepending historical narratives. Keep active/incomplete verification, unresolved process/operation IDs, exact authorization rows and the latest accepted slice visible. Preserve older evidence in dated same-directory documentation files with an index in the checkpoint; the frozen `docs/IMPLEMENTATION_STATE_ARCHIVE_2026-10-07.md` retains the complete pre-cleanup history. Read archives only when the current card requires them; canonical plan/decision/task/backlog authority and every acceptance gate remain unchanged. A commit hash can aid recovery when available, but commits are not mandatory checkpoints and must never be created without the user's request.

### Resume reconciliation, including a hard crash

1. Read root guidance and checkpoint. Confirm authorized scope and active/blocked task. Load source context for that task and its dependencies.
2. Inspect the actual tree. If Git exists, inspect branch/status/diff/recent history. If it does not, use the changed-file list and direct reads; never assume untracked files are disposable or initialize Git implicitly.
3. Compare recorded work to files, migrations and environment. A stale checkpoint is a lead, not proof. Record work found on disk as **recovered, unverified** until checked. Preserve unrelated edits and investigate conflicts rather than overwriting them.
4. Check listed processes, services, jobs and external effects before rerunning operations. If a migration, payment action, publication or provider job may already have happened, query its authorized status/reconcile its idempotency record first. Unknown outcome is not a reason for a blind retry.
5. Reuse passing evidence when its source/configuration is unchanged. Run a smallest relevant baseline check only for recovered unverified edits, changed dependencies or a concrete suspected failure; a new session alone requires no test. If unavailable, record the blocker and avoid marking the actual dependent work complete.
6. Repair or finish the partial slice, then update the card/TODO/checkpoint. Choose the next dependency-ready task within scope.

No Markdown workflow can preserve unsaved editor buffers or an external action whose result was never recorded. Frequent on-disk checkpoints plus actual-state reconciliation limit that loss; never invent an exact stopping point when evidence is missing.
